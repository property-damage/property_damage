# Scaffold Templates

How spec sections become files. You write these files directly (never via
`mix pd.gen.*` - their flags cannot carry the spec). Every generated file
opens with a header comment naming its regeneration class; keep the wording:

- regenerable: `# Generated by pd-model-interview from model_spec.md (class: regenerable).`
- adapter: `# Scaffolded by pd-model-interview (class: hand-owned). Yours after the first edit.`

Layout per model (from the spec's `dir:`): `model.ex`, `commands/` (one file
per command), `events/` (one per event), `projections/` (one per projection),
`simulator.ex`, `smoke.exs`, `adapter.ex`, and, when the spec has injected
events, an injector stub, next to `model_spec.md`. The dir lives under
`test/support/`, so run every mix command on it under `MIX_ENV=test` (see
"The smoke run" below).

Every generated module carries a `@moduledoc` written from the spec's prose
for that item, and every `@check` and `@eventually` function carries a `@doc`
written from the invariant's prose. Write them in the domain's words. The
failure report prints this text under "What this checks", and `mix pd.explain`
cites it as evidence. A module with no doc prints a "no description" gap line
instead, and an explanation cannot cite a gap as evidence.

In every module that uses a PropertyDamage macro (`use PropertyDamage.Command`,
`.Model`, `.Model.Projection` or `.Adapter`), the `use` line comes before the
first `def`, the adapter included, and before any other `use` that defines
functions. A module that breaks the rule does not compile.

The worked example below is a complete miniature model - a wallet service -
in exactly the shape the scaffold should produce. Its code blocks are
executed by the repository's doc-verification gate against the current
framework, so if these templates compile and run, your scaffold built from
them will too.

## The spec being scaffolded (excerpt)

```yaml
model: Wallets
namespace: MyStore.PD.Wallets
transport: in_process
reset: fresh instance per adapter setup
```

Commands: `OpenWallet` (sync, no fields, events: [WalletOpened]) and
`Deposit` (sync, fields: `wallet_id` (an existing wallet), `amount`
("positive cents"), when: "at least one wallet exists", weight: 3,
events: [Deposited]). Invariant `no_negative_balance` (check, after each event that moves a balance).

## The system under test

The real SUT is the user's application. Here a tiny in-process stand-in keeps
the example self-contained:

<!-- pd-doc-verify: runnable -->
```elixir
defmodule MyStore.WalletService do
  # Stand-in SUT. In a real project this module already exists - it IS the
  # system; the adapter below is the only place that touches it.
  def start_link, do: Agent.start_link(fn -> %{} end)
  def stop(pid), do: Agent.stop(pid)

  def open_wallet(pid) do
    id = "w_#{System.unique_integer([:positive])}"
    Agent.update(pid, &Map.put(&1, id, 0))
    {:ok, id}
  end

  def deposit(pid, id, amount) when is_integer(amount) and amount > 0 do
    Agent.get_and_update(pid, fn wallets ->
      case wallets do
        %{^id => balance} ->
          {{:ok, balance + amount}, %{wallets | id => balance + amount}}

        _ ->
          {{:error, :unknown_wallet}, wallets}
      end
    end)
  end
end
```

## Commands

Generator notes from the spec become StreamData generators. A field that
references an existing entity (`wallet_id`) defaults to `nil` here; the
model's `overrides:` option supplies it from projection state.

<!-- pd-doc-verify: runnable -->
```elixir
# test/support/pd/wallets/commands/open_wallet.ex
# Generated by pd-model-interview from model_spec.md (class: regenerable).
defmodule MyStore.PD.Wallets.Commands.OpenWallet do
  @moduledoc """
  Open a new, empty wallet.
  """

  use PropertyDamage.Command,
    observables: [MyStore.PD.Wallets.Events.WalletOpened]

  defstruct []

  @impl true
  def generator(_overrides \\ %{}), do: StreamData.constant(%{})
end

# test/support/pd/wallets/commands/deposit.ex
# Generated by pd-model-interview from model_spec.md (class: regenerable).
defmodule MyStore.PD.Wallets.Commands.Deposit do
  @moduledoc """
  Deposit a positive amount of cents into an existing wallet.
  """

  use PropertyDamage.Command,
    observables: [MyStore.PD.Wallets.Events.Deposited]

  import PropertyDamage.Generator, only: [merge_overrides: 2]

  defstruct [:wallet_id, :amount]

  @impl true
  def generator(overrides \\ %{}) do
    %{
      # spec: "an existing wallet" -> supplied by the model's overrides: option
      wallet_id: nil,
      # spec: "positive cents"
      amount: StreamData.positive_integer()
    }
    |> merge_overrides(overrides)
    |> StreamData.fixed_map()
  end
end
```

The spec's `events:` list becomes the `observables:` option of `use`: the
event modules the command can produce. Without it, `mix pd.validate --strict`
warns that event coverage is not verified, and the ladder fails.

Spec `execution:` maps to further `use` options: `sync` is the default;
`probe` and `async` add `execution: :probe` (or `:async`) to the same `use`
call, as in `use PropertyDamage.Command, execution: :probe, observables: [...]`.
The `execution:` and `shrink:` options are independent: `execution: :probe`
does not imply a shrink priority. A command whose spec block says
`shrink: prefer_remove` (a read-only command) writes `shrink: :prefer_remove`,
which makes the shrinker drop it first. `neutral` is the default, so the spec's
`neutral` writes nothing.

## Projections

State exists because a guard or an invariant needs it - nothing speculative.

<!-- pd-doc-verify: runnable -->
```elixir
# test/support/pd/wallets/projections/model_state.ex
# Generated by pd-model-interview from model_spec.md (class: regenerable).
defmodule MyStore.PD.Wallets.Projections.ModelState do
  @moduledoc """
  Which wallets exist, with their last known balance. The model's guards and
  overrides read it to pick an existing wallet.
  """

  use PropertyDamage.Model.Projection

  alias MyStore.PD.Wallets.Events.{Deposited, WalletOpened}

  @impl true
  def init, do: %{wallets: %{}}

  @impl true
  def apply(state, %WalletOpened{wallet_id: id}) do
    put_in(state, [:wallets, id], 0)
  end

  def apply(state, %Deposited{wallet_id: id, balance: balance}) do
    put_in(state, [:wallets, id], balance)
  end

  def apply(state, _), do: state
end

# test/support/pd/wallets/projections/balance_invariants.ex
# Generated by pd-model-interview from model_spec.md (class: regenerable).
defmodule MyStore.PD.Wallets.Projections.BalanceInvariants do
  @moduledoc """
  Tracks every wallet's balance so the checks can see money that left the books.
  """

  use PropertyDamage.Model.Projection

  alias MyStore.PD.Wallets.Events.{Deposited, WalletOpened}

  @impl true
  def init, do: %{balances: %{}}

  @impl true
  def apply(state, %WalletOpened{wallet_id: id}) do
    put_in(state, [:balances, id], 0)
  end

  def apply(state, %Deposited{wallet_id: id, balance: balance}) do
    put_in(state, [:balances, id], balance)
  end

  def apply(state, _), do: state

  @doc """
  No wallet ever holds a negative balance. A violation means money left the
  books, which is catastrophic.
  """
  # spec invariant: no_negative_balance (check, after every event that moves a balance).
  # Naming the events lets `mix pd.validate --strict` see them as handled.
  @check every: [WalletOpened, Deposited]
  def assert_no_negative_balance(state, _cmd_or_event) do
    case Enum.find(state.balances, fn {_id, balance} -> balance < 0 end) do
      nil -> :ok
      {id, balance} -> PropertyDamage.fail!("negative balance", wallet: id, balance: balance)
    end
  end
end
```

An `@eventually` invariant (eventual consistency) has this shape instead. The
function returns a predicate over the state, and the engine calls the
predicate at every interval until the timeout. Its return has three outcomes:

- truthy: the invariant holds, and the window ends;
- `false` or `nil`: not yet, so the engine tries again at the next interval,
  and fails the check when the timeout passes;
- `{:fail, reason}`: never, so the check fails at once with that reason.

A raise in the predicate also fails the check at once. Write a total
predicate, one that returns a verdict for every state (`get_in/2`, `match?/2`,
or a `case` with a fallback clause) and never raises on a state that has not
caught up yet:

    @doc """
    A payment is confirmed within five seconds of being initiated.
    """
    @eventually after: PaymentInitiated, timeout: 5, interval: {100, :milliseconds}
    def payment_confirmed(_state, %PaymentInitiated{id: id}) do
      fn state ->
        case get_in(state, [:payments, id]) do
          :confirmed -> true
          :rejected -> {:fail, "payment #{id} was rejected"}
          _pending_or_unknown -> false
        end
      end
    end

A safety invariant ("this never happens too much") is a third shape: a check
that runs once, on the settled final state, with `@check at: :teardown`. Its
projection must accumulate evidence (a count, a maximum, a sticky flag)
instead of holding the latest value, because a transient overshoot that heals
before the run ends leaves no trace in a snapshot:

    @doc """
    No payment is applied more than once.
    """
    @check at: :teardown
    def applied_at_most_once(state, _phase) do
      state.max_applications <= 1 or
        PropertyDamage.fail!("a payment was applied twice", max: state.max_applications)
    end

## Simulator

During sequence generation the engine asks the model's simulator what events
each command will produce, and the generation projection applies them. Without
a simulator no command predicts any event, so state never changes and every
command whose guard needs state (here `Deposit`, which needs a wallet) is
never generated.

The simulator is generated from the spec's command `events:` lists (the
simulate contract): each command's list becomes one `simulate/2` clause that
returns those events. A field marked `external` keeps its struct default
(`external()`); a field marked `from_command` copies the command's field. If
`events:` lists a rejection as well, the clause picks the event from the
`state` argument, the same way the SUT decides. The catch-all clause returns
`[]` for any command with no predictable events.

<!-- pd-doc-verify: runnable -->
```elixir
# test/support/pd/wallets/simulator.ex
# Generated by pd-model-interview from model_spec.md (class: regenerable).
defmodule MyStore.PD.Wallets.Simulator do
  @moduledoc """
  Predicts the events each wallet command produces, so the generator can plan
  ahead without calling the service.
  """

  @behaviour PropertyDamage.Model.Simulator

  alias MyStore.PD.Wallets.Commands.{Deposit, OpenWallet}
  alias MyStore.PD.Wallets.Events.{Deposited, WalletOpened}

  @impl true
  def simulate(%OpenWallet{}, _state), do: [%WalletOpened{}]

  def simulate(%Deposit{wallet_id: id, amount: amount}, _state) do
    [%Deposited{wallet_id: id, amount: amount}]
  end

  def simulate(_command, _state), do: []
end
```

## Model

Spec `when:` prose becomes the `when:` guard; entity-reference fields get
their `overrides:` option; spec weights carry over. The model's `@moduledoc`
comes from the spec's system overview, and the failure report prints it as
the model's description.

<!-- pd-doc-verify: runnable -->
```elixir
# test/support/pd/wallets/model.ex
# Generated by pd-model-interview from model_spec.md (class: regenerable).
defmodule MyStore.PD.Wallets.Model do
  @moduledoc """
  A wallet service: wallets open empty and take deposits. The model covers
  opening and depositing; withdrawals are not modeled yet.
  """

  use PropertyDamage.Model

  alias MyStore.PD.Wallets.Commands.{Deposit, OpenWallet}
  alias MyStore.PD.Wallets.Projections.{BalanceInvariants, ModelState}

  @impl true
  def commands do
    [
      {OpenWallet, weight: 1},
      {Deposit,
       weight: 3,
       # spec: "at least one wallet exists"
       when: fn state -> map_size(state.wallets) > 0 end,
       overrides: fn state ->
         %{wallet_id: StreamData.member_of(Map.keys(state.wallets))}
       end}
    ]
  end

  @impl true
  def command_sequence_projection, do: ModelState

  @impl true
  def check_projections, do: [BalanceInvariants]

  @impl true
  def simulator, do: MyStore.PD.Wallets.Simulator

  # Events that reach the test from outside, not as the result of a command
  # (webhooks, callbacks), are listed here and delivered by an injector. The
  # worked example has none, so the list is empty.
  @impl true
  def injectable_events, do: []
end
```

The spec marks an event `source: injected` when no command returns it: an
async command finishes later, and the system reports that through a webhook or
callback. Such an event is exempt from the rule that a command's `events:`
list produces every event. List it in `injectable_events/0` and give it an
injector. The injector stays hand-owned like the adapter, so scaffold a stub
and let the user fill in the transport:

<!-- pd-doc-verify: runnable -->
```elixir
# test/support/pd/wallets/payment_webhook.ex
# Scaffolded by pd-model-interview (class: hand-owned). Yours after the first edit.
defmodule MyStore.PD.Wallets.PaymentWebhook do
  @moduledoc """
  Delivers the payment provider's confirmation webhook as a PaymentConfirmed event.
  """

  use PropertyDamage.Adapter.Injector

  @emits [MyStore.PD.Wallets.Events.PaymentConfirmed]

  @impl true
  def setup(config) do
    # TODO(pd-model-interview): start listening for the webhook, and call
    # deliver(payload, queue) for each payload it receives.
    {:ok, %{queue: config.event_queue}}
  end

  @impl true
  def teardown(_context), do: :ok

  @impl true
  def to_event(_payload) do
    # TODO(pd-model-interview): turn the payload into a PaymentConfirmed event.
    :skip
  end

  # The queue stores whatever it receives as the event and the framework
  # never calls to_event/1 for an injector, so convert before pushing.
  def deliver(payload, queue), do: push_result(to_event(payload), queue)

  # Public on purpose. While to_event/1 returns only :skip, the compiler
  # warns that two clauses of a private function never match.
  def push_result({:ok, event}, queue),
    do: PropertyDamage.EventQueue.push(queue, __MODULE__, event)

  def push_result(:skip, _queue), do: :ok

  def push_result({:error, reason}, _queue) do
    raise "#{inspect(__MODULE__)}: to_event/1 returned an error: #{inspect(reason)}"
  end
end
```

The `raise` runs in the process that calls `deliver/2`, which is the user's
listener, not the run. If the listener lets it end that process (a webhook
server's request process, for one), the run never sees the error: it sees only
a missing event. The library has no channel from the listener to the run, so
the user builds one: the listener sends the failure to a named process, and
the adapter checks that process in `execute/3` and raises. An exception that
`execute/3` raises fails the run as an adapter error with its message.

Attach the injector to the target with `injectors:`, in the first-run
command (`targets: [{MyStore.PD.Wallets.Adapter, injectors:
[MyStore.PD.Wallets.PaymentWebhook]}]`) and in the ladder. There,
`mix pd.validate` takes `--targets` in place of the positional adapter
(`--targets '[{MyStore.PD.Wallets.Adapter, injectors:
[MyStore.PD.Wallets.PaymentWebhook]}]'`), and the smoke run uses the same
`targets:` form in its `PropertyDamage.run` call. Without the injector,
validation and the smoke run fail with "Injectable event
MyStore.PD.Wallets.Events.PaymentConfirmed not covered by any InjectorAdapter
@emits".

Time the transport. The framework drains the injector's event queue after
each command and once more after the last command, and neither drain waits for
a transport that has not delivered yet. The `at: :teardown` checks run right
after that last drain, before `teardown/1` of the adapter and of the injector.
An event that arrives later, even 50 ms later, is never folded into the state
the check reads. Two outcomes follow:

- A check that needs the event (the payment was confirmed) fails with a
  check failure that names the check, and the event log shows no such event.
  The failure points at the check, but the system did nothing wrong.
- A check that holds while the event is absent (at most one confirmation)
  passes without a word, so a real overshoot that arrives late goes unseen.

Flushing in `teardown/1` is too late, because the check has already run. Make
the event arrive before the last drain instead. Either of these works:

- Have `execute/3` of the command that triggers the transport wait until the
  transport has delivered (a monitor on the delivering process, a reply from
  the listener), and return its events afterwards. The next drain then holds
  the injected event.
- Add an `@eventually` for the operation, such as "after `PaymentInitiated`,
  the confirmation counter catches up". The run waits for it, within its
  `timeout:`, before the teardown checks run, and a timeout is reported as
  a poll timeout that names the operation.

When the spec lists setup or teardown commands (fixtures), the model also
defines `setup_each/0` and `teardown_each/0`. They take the same entries as
`commands/0`, but every entry runs, in the order written, before the first
root (setup) or after the last one (teardown); `when:` and `weight:` are
ignored there. A fixture command that no root needs does not appear in
`commands/0`. For a spec that lists "an admin user exists" as a fixture:

    @impl true
    def setup_each do
      [
        # spec fixture: "an admin user exists"
        {CreateUser, overrides: %{role: "admin"}}
      ]
    end

    @impl true
    def teardown_each, do: [DeleteTestUsers]

Omit both callbacks when the spec lists no fixtures. Resets that need no
fixture belong in the adapter's `setup/1`.

When the spec lists a `deferred` comparison or expansion (see the spec
format), leave `expansions/0` and `@compare` out and carry the note in the
model's `@moduledoc`.

## Adapter

Hand-owned after the first scaffold. Confirmed wiring gets real clauses;
everything unconfirmed is a TODO stub that raises loudly.

`setup/1` runs once per run in every target, so it must be idempotent, and
it does only what the adapter can do alone: start or reset the system, open
a connection. A fixture that the model's commands depend on ("what must exist
before anything can happen?") is a setup command in the model's
`setup_each/0`, never code in `setup/1`.

<!-- pd-doc-verify: runnable -->
```elixir
# test/support/pd/wallets/adapter.ex
# Scaffolded by pd-model-interview (class: hand-owned). Yours after the first edit.
defmodule MyStore.PD.Wallets.Adapter do
  @moduledoc """
  Runs the wallet commands against the in-process wallet service.
  """

  use PropertyDamage.Adapter

  alias MyStore.PD.Wallets.Commands.{Deposit, OpenWallet}
  alias MyStore.PD.Wallets.Events.{Deposited, WalletOpened}

  @impl true
  def setup(_config) do
    # spec reset strategy: fresh instance per adapter setup. Idempotent:
    # every call starts its own instance.
    {:ok, sut} = MyStore.WalletService.start_link()
    {:ok, %{sut: sut}}
  end

  @impl true
  def teardown(%{sut: sut}), do: MyStore.WalletService.stop(sut)

  @impl true
  def execute(%OpenWallet{}, %{sut: sut}, _runtime) do
    {:ok, wallet_id} = MyStore.WalletService.open_wallet(sut)
    {:ok, [%WalletOpened{wallet_id: wallet_id}]}
  end

  def execute(%Deposit{wallet_id: id, amount: amount}, %{sut: sut}, _runtime) do
    {:ok, balance} = MyStore.WalletService.deposit(sut, id, amount)
    {:ok, [%Deposited{wallet_id: id, amount: amount, balance: balance}]}
  end
end
```

## The smoke run

Only run in-session when every executed command's wiring was user-confirmed.
Bounded: this is proving the pipe (generate → execute → project → assert),
not hunting bugs yet.

Run it under `MIX_ENV=test`, because the scaffold lives in `test/support/`,
which the host project compiles for the `:test` environment only. Save the
script below as `smoke.exs` next to the spec and run
`MIX_ENV=test mix run test/support/pd/<slug>/smoke.exs`. Every ladder
rung (`mix compile`, `mix pd.validate`, the smoke run, the first real run)
runs under `MIX_ENV=test` for the same reason.

When the spec has injected events, write the target in `smoke.exs` as
`targets: [{MyStore.PD.Wallets.Adapter, injectors:
[MyStore.PD.Wallets.PaymentWebhook]}]`. The fence below has no injected
event and keeps the plain adapter.

The run also checks that every command in `commands/0` executed at least
once. A command whose guard never opens is never generated, and the run still
passes, so a pass alone proves nothing about that command. The check counts
`[:property_damage, :command, :start]` events and raises, naming each command
that never ran. The commands run in another process, so the counts live in an
`Agent`. The handler is a named module function, because `:telemetry` logs an
info notice on every run for an anonymous one.

<!-- pd-doc-verify: runnable -->
```elixir
defmodule SmokeCounts do
  @moduledoc false

  # A named handler: telemetry logs an info line for an anonymous one.
  def handle_event(_event, _measurements, %{command: command}, agent) do
    Agent.update(agent, &Map.update(&1, command, 1, fn n -> n + 1 end))
  end
end

model = MyStore.PD.Wallets.Model

listed =
  Enum.map(model.commands(), fn
    {module, _opts} -> module
    module -> module
  end)

{:ok, counts} = Agent.start_link(fn -> %{} end)

:telemetry.attach(
  "smoke-run-command-counts",
  [:property_damage, :command, :start],
  &SmokeCounts.handle_event/4,
  counts
)

result =
  try do
    PropertyDamage.run(
      model: model,
      targets: [MyStore.PD.Wallets.Adapter],
      max_runs: 15,
      max_commands: 8
    )
  after
    :telemetry.detach("smoke-run-command-counts")
  end

{:ok, _stats} = result

executed = Agent.get(counts, & &1)
per_command = Map.new(listed, fn module -> {module, Map.get(executed, module, 0)} end)

case Enum.filter(per_command, fn {_module, n} -> n == 0 end) do
  [] ->
    IO.inspect(per_command, label: "commands executed")

  never ->
    raise "commands never executed: #{inspect(Enum.map(never, &elem(&1, 0)))}; " <>
            "counts: #{inspect(per_command)}"
end
```

## The first real run

The hand-over names this command. It sets `report_html:`, so a failing run
writes its report as an HTML page (plus an `index.html` that lists every page
in the directory), which is the form the user and the explain skill read:

    MIX_ENV=test mix run -e '{:ok, _stats} = PropertyDamage.run(model: MyStore.PD.Wallets.Model, targets: [MyStore.PD.Wallets.Adapter], max_runs: 100, report_html: "_build/pd_reports")'

The `{:ok, _stats} =` match makes a failing run exit non-zero. Open
`_build/pd_reports/index.html` to browse the pages.

`PD_REPORT_HTML=_build/pd_reports` in the environment does the same for every
run of a test suite. A model that compares several targets lists each one in
`targets:` (`targets: [A.Adapter, {B.Adapter, name: "b"}]`) and marks the
compared observations with `@compare` in a check projection (see the
"Boundary Observations" section of the `PropertyDamage.Model.Projection`
docs). A model that lets a root run as one of several equivalent command
sequences defines `expansions/0` in the model. Scaffold
either one only when the spec records the user's yes, and leave a
`deferred` note in the model's `@moduledoc` otherwise.

## Editing this file

The tagged fences above run in the doc-verification gate
(`elixir scripts/docs_verify.exs`) inside a fresh consumer project: keep them
self-contained (no repo-internal paths), keep the
`<!-- pd-doc-verify: runnable -->` marker on the line immediately above each
fence, and remember elixir fences accumulate top-to-bottom within this file -
later fences see earlier modules. If you change a template, run the gate.
